PARTE 1: Automatización de Infraestructura y Orquestación con n8n

1.1. Fundamentos Teóricos de n8n e iPaaS

n8n es un orquestador de flujos de trabajo (*Workflow Automation*) de código abierto clasificado dentro del modelo iPaaS (Integration Platform as a Service). En el ecosistema de SmartGymBro se ejecuta autohospedado (*on-premise*) mediante el contenedor Docker gymbro-n8n sobre la red interna gymbro-n8n-net.

A diferencia de servicios comerciales cerrados en la nube (como Zapier o Make), el despliegue local garantiza tres propiedades críticas:

  • Soberanía de Datos: Ni los respaldos de la base de datos, ni las trazas de infraestructura ni las claves de autenticación salen a la nube pública.
  • Latencia Mínima y Red Local: n8n se comunica con Prometheus, MantisBT, Nextcloud y PostgreSQL a velocidad de red local usando el DNS interno de Docker (host.docker.internal).
  • Ejecución y Extensibilidad Ilimitadas: Permite escribir transformaciones en JavaScript estándar y no cobra costos por volumen de tareas ejecutadas.

Conceptos Esenciales de la Arquitectura de n8n

  • DAG (Grafo Dirigido Acíclico): Los flujos se componen de nodos ordenados secuencialmente o en paralelo que procesan información de izquierda a derecha.
  • Estructura de Datos JSON: Todo dato que viaja entre nodos se encapsula en una lista de objetos JSON con la propiedad json (ej. $input.all()[0].json).
  • Mecanismos de Activación (Triggers): Pueden ser Polling/Schedule (consultas cíclicas por tiempo) o Webhooks (recepción reactiva de peticiones HTTP POST).
  • Doble Persistencia (Entidad vs Historial): n8n guarda los flujos en su SQLite interno (database.sqlite). La tabla workflow_entity almacena el borrador de diseño visual, mientras que workflow_history y workflow_published_version almacenan la versión compilada que realmente ejecuta el motor en segundo plano cuando el flujo está Published (Activo).

1.2. Cómo se Construye e Implementa un Flujo en el Lienzo

Cualquier flujo de control o automatización en n8n sigue una metodología de 5 pasos secuenciales:

[ 1. Trigger (Inicio) ] ──► [ 2. HTTP Request / Ingesta ] ──► [ 3. Code (Lógica JS) ] ──► [ 4. IF (Control) ] ──► [ 5. Acción Final ]
  1. Disparador (Trigger): Se define cuándo corre el proceso (ej. un nodo Schedule Trigger configurado cada 30 segundos).
  2. Ingesta de Información: Un nodo como HTTP Request consulta una API REST (ej. GET /api/v1/rules de Prometheus).
  3. Procesamiento y Limpieza (Code Node): Mediante JavaScript se accede a los datos anteriores, se aplican filtros y se preparan las variables de salida: 
    const items = $input.all();
return items.map(item => ({
  json: {
    nombre: item.json.name,
    esCritico: item.json.severity === 'critical',
    timestamp: new Date().toISOString()
  }
}));
  4. Toma de Decisiones (Nodo IF): Evalúa una expresión booleana (ej. {{ $json.esCritico }} == true) bifurcando el camino en True y False.
  5. Salida Operativa: Creación de tickets en MantisBT, envío de mails por SMTP o almacenamiento en Nextcloud vía WebDAV.

1.3. ¿Cómo Implementar un Flujo con IA y Base Vectorizada (RAG)?

Pregunta de Examen: "Diseñe un flujo de control que responda dudas técnicas usando un nodo de IA y una base vectorizada"

El patrón requerido es RAG (Retrieval-Augmented Generation / Generación Aumentada por Recuperación). En lugar de permitir que la IA invente datos, la IA consulta una base de datos vectorial que contiene la documentación técnica del proyecto antes de generar su respuesta.

Arquitectura de Implementación en n8n:

[ Webhook / Chat Trigger ] ──► [ AI AGENT (Orquestador Central) ] │ ├── [ Model: Google Gemini / OpenAI Chat Model ] ├── [ Vector Store Tool: PostgreSQL pgvector / Qdrant ] │ └── [ Embeddings: Text-Embedding-004 ] └── [ Memory: Window Buffer Memory (Historial) ]

Pasos para construirlo en el lienzo de n8n:

  1. Nodo Central: Se arrastra el nodo AI Agent (sección Advanced AI). Es el coordinador del razonamiento.
  2. Conectar el Modelo de Lenguaje: Al subconector inferior Model del AI Agent, se conecta el nodo Google Gemini Chat Model (o OpenAI Chat Model). Se configura la API Key y se fija una temperatura baja (temperature = 0.2) para evitar alucinaciones.
  3. Conectar la Base Vectorizada: Al subconector Tool o Vector Store, se conecta PostgreSQL Vector Store (con la extensión pgvector) o Qdrant.
  4. Conectar el Modelo de Embeddings: Al nodo de Vector Store se le vincula un subnodo Embeddings. Este traduce las preguntas humanas a vectores matemáticos para calcular similitud semántica.
  5. Prompt de Control del Sistema (System Message): Dentro del AI Agent se establece la directiva inquebrantable de gobernanza: 
    Eres el Asistente Técnico de Operaciones de SmartGymBro.
REGLAS OBLIGATORIAS:
1. Responde ÚNICAMENTE utilizando el contexto recuperado de la base vectorizada.
2. Si la respuesta no está en los documentos recuperados, responde textualmente:
   "No dispongo de evidencia en la base de conocimiento para responder a esta consulta."
3. Cita siempre el componente o contenedor de referencia.

1.4. Los 4 Flujos Implementados en SmartGymBro

  • WF1 – Alertas de Infraestructura en Tiempo Real: Centinela reactivo. Consulta cada 30s a Prometheus (/api/v1/rules). Cuando detecta ContainerDown, PostgresDown o BackendDown, ejecuta deduplicación con marca temporal (startsAt vs created_at) y abre incidencias en MantisBT asignadas al especialista por categoría (facundo_db, gonzalo_dev, etc.) con severidad crash.
  • WF2 – Auditoría Diaria de Backups: Cron diario a las 03:00 hs. Lee /data/pg-backups/, verifica tamaño y ejecuta pg_restore --list para comprobar la cabecera e integridad de los datos. Si falla, despacha un correo de alarma SMTP a Sonia.
  • WF3 – Informe Semanal de Rendimiento y Heurística con IA: Lee latencia HTTP, disponibilidad de /api/health, reinicios y memoria. Envía las métricas al contenedor gymbro-informe-analyzer (Python) para clasificar el riesgo (OK, WARN, CRIT), sube el reporte a Nextcloud vía WebDAV y notifica a supervisores.
  • WF-RESTORE – Prueba Controlada de Restauración: Valida que los backups sean restaurables. Descarga el dump e impacta las tablas en el contenedor efímero gymbro-pgrestore-test (PostgreSQL 17 en memoria RAM tmpfs) sin tocar la base productiva.

PARTE 2: Ciberseguridad Aplicada, Hardening y Gestión de Incidencias

2.1. Marco Teórico: Tríada CIA y OWASP Top 10

La seguridad del sistema SmartGymBro se diseñó alineada a la Tríada CIA:

  • Confidencialidad: Los historiales de pesaje, rutinas privadas y contraseñas (cifradas con bcrypt) no deben ser accesibles entre atletas ni filtradas en errores.
  • Integridad: Protección de tokens JWT mediante firmas criptográficas inviolables para evitar falsificación de identidad de usuario.
  • Disponibilidad: Protección del cluster de PostgreSQL (Patroni/etcd) y límites de payload para neutralizar ataques de denegación de servicio (DoS).

Riesgos del OWASP Top 10 Mitigados:

  • A01: Broken Access Control: Desarrolladores restringidos a ver únicamente sus tickets asignados en MantisBT.
  • A02: Cryptographic Failures: Rechazo de tokens con algoritmos no autorizados o firmas no validadas.
  • A03: Injection (SQLi): Consultas parametrizadas en Sequelize y neutralización de entradas maliciosas.
  • A05: Security Misconfiguration: Fuga de consultas SQL en respuestas 500 y exposición de huella tecnológica mediante X-Powered-By.

2.2. Implementación Técnica de Auditoría SAST (`npm audit` y remediación)

Se ejecutó un análisis estático de seguridad en el código y árbol de dependencias mediante npm audit:

  • Diagnóstico Inicial: Se detectaron 63 vulnerabilidades. El 60% se concentraba en versiones deprecadas de Angular 19 (fallas de XSS en @angular/compiler) y paquetes backend con potencial DoS (body-parser 2.3.0 y fugas de memoria en zod).
  • Remediación Aplicada:
    • Actualización de parches compatibles: body-parser $\rightarrow$ 2.4.0, proxy-addr $\rightarrow$ 2.0.8, moment $\rightarrow$ 2.31.0.
    • Mitigación a nivel de aplicación para Zod: Se fijó en Express un tamaño máximo de cuerpo JSON (app.use(express.json({ limit: '1mb' }))) para impedir el desbordamiento de memoria por colecciones gigantes.
    • Migración a versión soportada de Angular: Eliminó el 100% de las fallas de sanitización del DOM, reduciendo el reporte de 63 a 26 advertencias residuales únicamente de herramientas locales fuera del código del cliente.

2.3. Blindaje de la API en Node.js/Express (Hardening de Código)

1. Eliminación de Fuga de Información (Information Disclosure en app.js):

// Middleware global de errores seguro (4 parámetros)
app.use((err, req, res, next) => {
  // 1. Log interno en consola del servidor para diagnóstico DevOps
  console.error(`[ERROR INTERNO] Tipo: ${err.name} | Ruta: ${req.method} ${req.path}`);

  // 2. Respuesta opaca hacia el cliente: jamás exponer err.sql ni err.message
  const status = err.status || 500;
  res.status(status).json({
    error: 'Error interno del servidor',
    codigo: status,
    mensaje: 'La solicitud no pudo procesarse. El incidente ha sido registrado para auditoría.'
  });
});

2. Validación Estricta de JWT en middlewares/auth.js:

const jwt = require('jsonwebtoken');

function requireAuth(req, res, next) {
  const header = req.headers['authorization'];
  
  // Exigir obligatoriamente el formato Bearer
  if (!header || !header.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Esquema de autenticación inválido. Formato: Bearer ' });
  }

  const token = header.split(' ')[1];
  try {
    // Forzar algoritmo HS256 y verificar con la clave del servidor
    const payload = jwt.verify(token, process.env.JWT_SECRET, { algorithms: ['HS256'] });
    
    // Validar presencia de identificador de usuario
    if (!payload.sub && !payload.id) {
      return res.status(401).json({ error: 'Token inválido: falta sujeto' });
    }

    req.user = payload;
    next();
  } catch (e) {
    return res.status(401).json({ error: 'Token expirado o firma criptográfica no válida' });
  }
}

3. Inyección de Cabeceras HTTP de Seguridad:

// Deshabilitar huella del servidor
app.disable('x-powered-by');

// Cabeceras protectoras contra Clickjacking y MIME-Sniffing
app.use((req, res, next) => {
  res.setHeader('X-Content-Type-Options', 'nosniff');
  res.setHeader('X-Frame-Options', 'DENY');
  res.setHeader('Referrer-Policy', 'no-referrer');
  res.setHeader('Cache-Control', 'no-store');
  next();
});

Mitigación: Se implementó un middleware de error centralizado que devuelve mensajes genéricos al cliente.

Mitigación: Actualización a body-parser 2.4.0 y límite de carga útil fijado en 1 MB.
#5 Ausencia de cabecera contra Clickjacking (X-Frame-Options) Minor Frontend aldo_front Impacto: La aplicación podía ser embebida en iframes invisibles en sitios web de terceros.

Mitigación: Configuración de borrado lógico (soft-delete) y cascadas referenciales en Sequelize.
#7 Riesgo de agotamiento de memoria por colecciones en Zod Major Backend gonzalo_dev Impacto: Arrays excesivamente anidados en creación de rutinas consumían la memoria del worker.
Mitigación: Restricción estricta de tamaño en Express y validación de máximo 20 items por lote.
#8 Falta de limitación de tasa (*Rate Limiting*) en endpoint de login Major Seguridad gonzalo_dev Impacto: Vulnerabilidad a ataques de fuerza bruta continuos contra el algoritmo bcrypt.
Mitigación: Planificación de middleware limitador de intentos por dirección IP y usuario.
#9 PostgresDown: Caída del nodo primario del cluster de base de datos Crash Database facundo_db Impacto: Caída total de lectura/escritura si no actuaba el failover.
Mitigación: Promoción automática de réplica a nuevo líder vía Patroni y apertura automática de ticket en WF1.
#10 ContainerDown: Detención o caída inesperada de contenedor Docker Crash Infra sonia_dev Impacto: Pérdida de un servicio de la aplicación.
Mitigación: Detección en Prometheus, deduplicación temporal en WF1 y notificación inmediata en MantisBT.
