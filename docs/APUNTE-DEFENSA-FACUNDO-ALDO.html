1. Exposición Pública con Túnel Seguro: Cloudflare Tunnel

1.1. ¿Cómo Funciona y qué Problema Resuelve?

En una arquitectura tradicional, exponer una aplicación web que corre en un entorno local (http://localhost:4300) hacia Internet requiere configurar el router (abrir puertos con Port Forwarding), disponer de una dirección IP pública estática y abrir el firewall del sistema operativo, exponiendo la red doméstica a escaneos de puertos y ciberataques.

Cloudflare Tunnel (mediante el agente cloudflared) implementa un modelo de túnel reverso cifrado:

  • Conexión Saliente: El cliente cloudflared inicia una conexión TCP/TLS saliente (puerto 443) hacia la red global de Cloudflare. Al ser tráfico saliente, no requiere abrir ningún puerto en el router ni en el firewall.
  • Enlace Público Seguro con HTTPS: Cloudflare asigna automáticamente un subdominio temporal bajo trycloudflare.com (modo Quick Tunnel) dotado de certificado SSL/TLS válido.
  • Aislamiento y Blindaje Perimetral: Únicamente se expone el puerto 4300 del servidor web Nginx (Frontend). La base de datos (PostgreSQL 5432) y la API interna (Node.js 3100) permanecen 100% aisladas en la red interna de Docker, inaccesibles desde el exterior.

1.2. ¿Está Dockerizado o es un Programa Instalado?

La Clave de la Arquitectura: Aplicación Dockerizada vs Túnel Híbrido

La aplicación web SmartGymBro está 100% dockerizada (Frontend Nginx, Backend Express y Cluster de PostgreSQL). Para conectar esa red de contenedores con Internet mediante Cloudflare Tunnel, existen dos formas de ejecución técnicamente equivalentes:

Modalidad Comando de Ejecución Características Operativas
Versión Dockerizada
(Recomendada Académica)		 docker run --rm -it cloudflare/cloudflared:latest tunnel --url http://host.docker.internal:4300 • El túnel corre dentro de un contenedor Docker aislado.
• No requiere instalar nada en Windows (cero dependencias en el host).
• El flag --rm destruye el contenedor al presionar Ctrl+C sin dejar basura en el disco.
• Usa host.docker.internal:4300 para puentear el tráfico hacia el Frontend publicado.
Versión Nativa Windows
(Ejecutable CLI)		 cloudflared tunnel --url http://localhost:4300 • Corre como ejecutable nativo en Windows instalado vía winget.
• Apunta directo a localhost:4300.
• No crea contenedores adicionales; consume menos de 20 MB de RAM.

Cómo Explicarlo en la Mesa de Examen ante el Profesor

«Profesor, la arquitectura está completamente contenida en Docker. Para el cumplimiento del Punto 9 (Publicación con Túnel Seguro), utilizamos un contenedor efímero de Cloudflare mediante la imagen oficial cloudflare/cloudflared. Al ejecutarse con --rm, se crea un túnel saliente cifrado por TLS que redirige las peticiones externas directamente al reverse proxy Nginx en el puerto 4300, manteniendo PostgreSQL y la API en una red privada sin abrir puertos en el router.»

2. Tareas Desarrolladas por Facundo: Base de Datos y Alta Disponibilidad (DBA)

2.1. Generación Masiva de Datos: 6 Millones de Registros (Punto 4)

  • Script Generador Sintético: Implementación de scripts batch en Node.js (seed-usuarios.mjs y seed-actividad.mjs) que poblaron la base de datos con 20.000 usuarios maestros y distribuyeron **6.000.000 de filas transaccionales** en la tabla gymbro.series_realizadas.
  • Estructura Relacional Realista: Cada registro contiene IDs UUID, marcas temporales históricas, ejercicios completados, pesos levantados y series asociadas a sesiones de entrenamiento reales.

2.2. Optimización y Rendimiento SQL con Índices B-Tree (Punto 5)

  • Diagnóstico con EXPLAIN ANALYZE: Análisis de los planes de ejecución sobre las 8 consultas críticas del backend antes de indexar, detectando cuellos de botella por escaneo secuencial masivo (Seq Scan) que tardaban más de 800 ms.
  • Indexación Estratégica: Creación de índices B-Tree específicos (ej. idx_series_usuario_fecha, idx_marcas_fuerza_ejercicio) que transformaron las consultas en búsquedas por índice (Index Scan / Bitmap Index Scan), logrando tiempos de respuesta de menos de 5 milisegundos.

2.3. Clúster de Alta Disponibilidad con Patroni, etcd y HAProxy (Punto 6)

  • Topología de 3 Nodos PostgreSQL 17: Despliegue de gymbro-db-node1, gymbro-db-node2 y gymbro-db-node3 en contenedores Docker independientes.
  • Orquestación y Consenso con Patroni y etcd: Cluster de 3 nodos etcd (consenso Raft). Patroni monitorea la salud de los nodos y gestiona la elección de líder.
  • Replicación Física por Streaming: Transmisión continua de los registros WAL en tiempo real desde el nodo Primario hacia las réplicas.
  • Failover Automático en < 30 Segundos: Si el nodo Primario se detiene, etcd detecta la pérdida de heartbeat y Patroni promueve automáticamente una réplica sana a nuevo Primario sin intervención manual ni pérdida de datos.
  • Balanceador HAProxy (Doble Puerto):
    • Puerto 55433 (Escritura): Envía las operaciones INSERT/UPDATE/DELETE exclusivamente al nodo Primario activo.
    • Puerto 55434 (Lectura): Distribuye consultas SELECT balanceadas entre los nodos réplica.

2.4. Automatización de Backups y Herramientas de Base de Datos

  • Contenedor de Respaldos: Daemon gymbro-postgres-backup programado para generar dumps periódicos de base de datos con pg_dump.
  • Gestión con pgAdmin 4: Servidor gymbro-pgadmin (puerto 5051) precargado con las conexiones al clúster y al balanceador HAProxy.
  • MantisBT: Configuración de campos personalizados y vistas segregadas para el rol de DBA (facundo_db).

3. Tareas Desarrolladas por Aldo: DevOps, CI/CD, Contenedores y Redes

3.1. Contenedorización de la Aplicación Web (Punto 7)

  • Backend Dockerfile: Imagen basada en node:24-alpine, optimizada para entorno monorepo (inclusión del paquete shared/), ejecución bajo usuario sin privilegios y arranque con Express.
  • Frontend Multi-Stage Dockerfile:
    • Stage 1 (Build): Compilación de Angular 22 en un entorno Node.js temporal.
    • Stage 2 (Runtime): Servidor Nginx Alpine ultraliviano que sirve la SPA y opera como Reverse Proxy, enrutando /api/ hacia el backend interno.
  • Compose Unificado: Diseño del docker-compose.yml maestro integrando redes, variables de entorno y mapeo de puertos.

3.2. Pipeline de CI/CD y Automatización en GitHub Actions (Punto 8)

  • Workflow Automatizado (.github/workflows/ci-cd.yml):
    • Etapa CI (Integración Continua): Descarga de código, instalación de dependencias y ejecución de pruebas unitarias automatizadas (validación en verde en < 1 minuto).
    • Etapa CD (Despliegue Continuo): Compilación de imágenes Docker y publicación multirregistro en Docker Hub (aldodante) y GitHub Container Registry (GHCR).
  • Guía de Rollback (docs/ROLLBACK.md): Protocolo operativo de contingencia para revertir versiones defectuosas mediante etiquetas versionadas.

3.3. Automatización con Watchtower y Scripts de Despliegue

  • Watchtower (gymbro-watchtower): Vigila el registro Docker Hub y actualiza automáticamente los contenedores en caliente al detectar una nueva versión de imagen.
  • Lanzadores de Despliegue: Creación de scripts batch (Interfaces_SmartGymBro.bat, Restaurar_Mantis_Notebook.bat) para el arranque coordinado de todo el stack en un clic.
